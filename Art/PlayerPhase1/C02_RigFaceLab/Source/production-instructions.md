# C02 리깅 개선 → 동작 개선 → 얼굴 표정 자동화 실험

## 목표와 사용자 지시

AutoPlayerV1의 C02를 후속 개발 대상으로 선택한다. C02의 품질을 이미 합격으로 인정한다는 뜻은 아니다. 기존 모델을 바탕으로 몸과 옷의 변형을 개선하고, 움직임을 자연스럽게 만든 다음, 얼굴 표정 리깅까지 단계적으로 구현·검증하라. 이번 작업은 실제 게임용 결과물을 얻는 동시에 Codex·Blender 자동화의 한계를 확인하는 실험이다.

나는 콘셉트·외형 지침과 결과에 대한 시각적 판단만 제공할 수 있다. 수동 모델링, 웨이트 페인팅, 리토폴로지, UV 수정, 리깅을 나에게 맡기지 마라. 계획 설명으로 끝내지 말고 연결된 프로젝트에서 수행 가능한 작업을 실행하라. 단계마다 허락을 다시 묻지 말고, 통과한 결과를 보존하며 다음 단계로 진행하라.

이 지시는 이번 C02 실험에 한해 과거 production-instructions.md의 ‘후보당 보정 2회 후 중단’, ‘국부 재구성 금지’, ‘보조본 금지’, ‘얼굴 리깅 제외’를 아래 범위로 변경한다. 과거 비용 한도와 후보 수를 초기화하여 새 모델을 생성하라는 지시가 아니다. 시스템·개발자 지침, 실제 도구 권한과 프로젝트 규칙을 준수하라.

## 1. 범위·보존·실행 한도

- 기존 C02 모델, Meshy 리그와 다운로드한 애니메이션을 재사용한다. 이번 추가 Meshy 및 외부 유료 요청 예산은 0이다. 새 캐릭터·리그·동작 생성, 유료 서비스 가입·결제는 실행하지 않는다. 로컬 도구와 이미 설치되어 사용 가능한 도구를 활용한다.
- 긴 두루마기, 얼굴 인상, 머리·수염, 체형과 핵심 배색을 보존한다. 짧은 옷 시안으로 자동 교체하지 않는다. 미세한 해짐과 잘못 연결된 면의 국부 정리는 허용하되 변경 부위를 보여라.
- 원본 AutoPlayerV1/C02, FitRigV3, 공용 PlayerRig와 C2 씬을 덮어쓰지 않는다. 새 작업 폴더와 별도의 Unity 실험 씬·프리팹에서 수행한다. 기본 출력 위치는 프로젝트 루트의 Art/PlayerPhase1/C02_RigFaceLab/이며, 실제 폴더 규칙에 맞춰 정하라.
- 기본 착의 캐릭터는 실제 렌더 삼각형 60,000개 이내를 유지한다. 얼굴의 국부 보강이 필요하면 기존 51,760개라는 보고 수치를 신뢰하지 말고 실제 남은 예산부터 확인하라. 이 수치와 아래 본·수정 횟수는 이번 실험의 예산이며 보편적인 품질 기준이 아니다.
- 몸/의복 변형 수정은 추가 최대 4회, 동작/보조 움직임은 최대 3회, 얼굴 기초는 최대 3회, 표정 확장은 최대 3회까지 실행한다. 횟수는 비교 가능한 수정 후보를 평가하는 단위이며 파일 저장 횟수가 아니다. 같은 원인에 대한 2회 시도에서 개선이 없으면 같은 조정을 반복하지 말고 다른 원인·방법을 검증하거나 해당 항목의 한계를 기록하라.
- 단계당 수정 횟수를 무제한 세분화하지 않는다. 다른 단계에서 앞 단계의 모델을 다시 수정하면 해당 단계의 남은 횟수를 사용한다. 이미 충분히 검증된 결과의 전체 렌더를 사소한 변경마다 반복하지 않는다.
- 이번에는 의상 교체, 완전한 옷 아래 신체 복원, 전신 리토폴로지, 대규모 얼굴 재제작, 대사 립싱크·음성 생성, 실시간 천 시뮬레이션 전체 구축을 목표로 삼지 않는다. 실제 붓이 프로젝트에 있으면 뒤 단계에서 파지를 시험하되, 없는 붓을 새로 유료 생성하여 작업을 확대하지 않는다.

## 2. 시작점 확인과 기준본

1. AGENTS.md 등 해당 프로젝트의 실제 지침을 읽고 Blender·Unity 버전, 사용 가능한 MCP/로컬 실행 경로를 확인한다. 불필요한 인증정보나 API 키를 출력하지 않는다. 기존 Blender의 저장되지 않은 변경이 있으면 보존한 뒤 별도 작업 파일을 연다.
2. AutoPlayerV1의 FINAL_REPORT.md, candidate_result.json, source_manifest.json 및 실제 파일을 찾아 C02 최신본을 식별한다. 보고서가 가리키는 파일은 Candidates/C02/Candidate_C02_Repaired.blend다. 실제 경로와 버전이 다르면 근거를 기록한다.
3. C02_Run_front.mp4 같은 파일명만으로 최신 보정 영상이라고 가정하지 않는다. Baseline과 Repair2의 모델·클립·텍스처 대응을 확인하고 불분명하면 선택한 실제 모델에서 기준 영상을 다시 렌더한다. 썸네일을 모델 데이터로 취급하지 않는다.
4. 원본을 보존하고 Baseline.blend와 작업 복사본을 만든다. 메시, UV, 재질, 사용 텍스처, 정지 골격 행렬, 웨이트, 클립 목록, 프레임 범위·fps를 기록한다. 새 리그를 무조건 다시 만들지 않는다.
5. 최신 C02에서 정면·측면·후면 정지 모습, 기존 Run·Idle·Attack과 경고 프레임을 확인한다. C01/C03의 실패 수치를 C02 수치로 섞지 않는다. 기존 C02는 잔여 늘어남 경고가 있는 UNVERIFIED 상태에서 시작한다.

## 3. 단계 A — 몸과 의복의 변형 개선

먼저 ‘같은 원본 동작에서 C02의 변형이 좋아졌는가’를 검증한다. 아직 동작 타이밍이나 팔의 가동 범위를 바꾸지 않는다.

진단은 다음 상태를 나누어 수행하라.

| 상태 | 확인할 내용 |
| --- | --- |
| 정지 메시 | 어깨·겨드랑이·소매·자락의 잘못 연결된 면, 겹친 면, 구멍, 고정된 돌출 |
| 기존 골격과 원본 클립 | 문제가 시작되는 본·프레임·정점 영역, 반대쪽 팔다리의 영향, 관절 부피 손실 |
| 수정한 웨이트/국부 메시 | 동일 클립에서 실제 개선과 다른 부위의 회귀 여부 |
| 후속 보조 변형 | 기초 스키닝과 별개로 얻은 개선 또는 새로 생긴 문제 |

- 우선순위는 겨드랑이와 어깨, 소매·팔꿈치, 다리에 끌리는 자락이다. 에지 경고를 실제 메시 위에 표시하여 문제 영역을 찾는다. 경고값만으로 자동 탈락시키거나 무해하다고 선언하지 않는다.
- 정규화만 하고 완료하지 않는다. 연결성·신체의 좌우·부위별 경계를 고려해 웨이트를 수정한다. 서로 가까운 반대쪽 다리나 다른 옷 층으로 최근접 웨이트를 무차별 전달하지 않는다.
- 겉옷을 신체에 전부 밀착시키지 않는다. 넓은 소매와 긴 자락의 의도된 공간을 유지한다. 다리를 드러내는 정상적인 앞트임과, 잘못 연결되어 늘어지는 띠를 구분한다.
- 원인이 확인되면 국부 연결 정리, 관절 주변 소규모 토폴로지 보강, 제한된 웨이트 재배치와 교정 형상키를 실험할 수 있다. 변경 영역·UV와 무늬의 영향·삼각형 증가를 기록한다. 수정과 무관한 얼굴·몸 부위를 재생성하지 않는다.
- 기존 핵심 골격의 정지 자세·본 이름·계층은 가능한 한 유지한다. 변경이 꼭 필요하면 별도 분기에서 기존 애니메이션과 바인드 관계를 검증한다. 원본 애니메이션을 조용히 덮어쓰지 않는다.
- Blender 전용 모디파이어나 드라이버로 좋아 보이면 내보낼 실제 변형 데이터로 표현할 방법도 확인한다. Blender 화면에서만 좋아진 결과를 Unity 합격으로 처리하지 않는다.
- 전체 Shrinkwrap, 무차별 용접, 팔 가동 범위 축소, 문제 프레임 삭제, 보이지 않게 카메라 변경 등의 방식으로 실패를 감추지 않는다.

평가는 원본 Walk·Run·Idle·Attack과 팔 내리기·깊은 팔꿈치 굽힘·머리 위 팔 올리기·몸통 비틀기·양발 접지 스쿼트에서 수행한다. 실제 없는 진단 동작만 로컬에서 추가하며, 원본 클립은 비교용으로 보존한다. 수치 검사는 전체 정수 프레임을 대상으로 하되 영상 검수는 우선 문제 구간과 대표 동작에 집중한다.

어깨 부피, 소매 접힘, 자락 형태, 정상적인 옷 틈과 비정상적인 개구를 같은 카메라·재질·조명에서 비교한다. 중립 회색 재질 검사와 원래 재질 검사를 함께 사용하여 형태와 무늬 문제를 구분한다. 통합 메시에서 신뢰할 만한 관통 대상을 정의하지 못하면 해당 수치는 UNVERIFIED로 남긴다. 임의의 에지 비율이나 양수 거리만으로 합격시키지 않는다.

## 4. 단계 B — 자연스러운 동작과 보조 움직임

단계 A의 가장 나은 검증본을 보존하고 진행한다. 원본 클립에서의 리깅 개선과 새 동작 편집의 효과를 각각 비교할 수 있게 하라.

- 원본 클립을 복제한 후 동작의 중심 이동, 팔 스윙, 발 접지, 루프 경계와 Idle↔Run 전환을 다듬는다. 발 미끄러짐을 볼 수 있도록 지면을 제공한다. 제자리 달리기와 루트 이동이 있는 클립을 구분하고 실제 캐릭터 이동 속도와 접지의 관계를 확인한다.
- 자연스러움은 리그만으로 결정되지 않는다. 동작 원본의 문제를 명시하고 수정본을 별도로 제공한다. 관통을 피하려고 기존 비교용 동작의 범위나 속도를 몰래 바꾸지 않는다.
- 기초 스키닝이 안정된 부위에만 소수의 자락·소매용 보조본 또는 교정 형상키를 추가할 수 있다. 의복용 새 변형 본은 최대 12개를 실험 예산으로 삼고, 각 본의 대상 영역과 목적을 기록한다. 먼저 적은 수로 효과를 확인한다.
- 넓은 천을 종아리 회전에 그대로 끌려가게 하거나 모든 자락을 골반에 고정하는 일괄 처방을 피한다. 휴지 상태의 형태, 다리와의 간격, 움직임에서의 반응을 함께 비교한다. 보조본을 추가했다는 사실 자체를 자연스러운 천 움직임이라고 표현하지 않는다.
- FitRigV3처럼 Cloth 프록시를 수십 개의 본에 근사 베이크하는 체계로 돌아가지 않는다. 이번 보조 움직임은 단순한 본/형상키 제어로 시험한다. 실제 시간에 반응하는 보조 움직임을 구현할 경우 초기화·클립 전환·급정지·회전·시간 간격 변화에서 튀거나 누적 변형되지 않는지 검증한다.
- 클립에 기록한 보조 움직임과 Unity에서 실제로 반응하는 보조 움직임을 구분한다. 런타임 제어기가 없는 클립 베이크를 실시간 의복 물리로 표시하지 않는다.
- 짧은 Run 1회만 확인하지 말고 최소 6주기의 원속도 반복, 시작/정지 전환, Idle→Run→Idle→Attack의 연속 구간을 확인한다. 원본 fps에 맞춰 재생하고 영상 fps를 바꿨다면 시간 길이가 유지되도록 처리한다.
- 손 리깅은 손가락을 굽혔다 펴는 검사부터 한다. 기존 붓이 있으면 손잡이 파지와 공격 중 접촉을 검사한다. 무기 없이 제공된 Attack 클립을 붓 파지 완료로 표시하지 않는다.

## 5. 단계 C — 얼굴 구조와 최소 표정 기능

몸/옷의 통과본을 별도 보존한 뒤 얼굴 실험 복사본을 만든다. 얼굴 작업 실패가 몸/옷 개선 결과를 덮어쓰지 않게 하라. 몸 단계가 한도 내에 해결되지 않더라도, 영향이 분리된 얼굴 기능의 독립 실험은 계속할 수 있다. 이 경우 최종 통합 캐릭터 합격으로 표시하지 않는다.

### 먼저 실제 구조를 확인한다

- 안구가 별도 기하인지, 얼굴 표면과 붙어 있는지, 눈이 텍스처에만 그려져 있는지 확인한다.
- 눈꺼풀 가장자리와 안구 간격, 입술 경계와 연결 상태, 턱을 움직일 영역, 입안의 존재 여부를 확인한다.
- 얼굴·수염·눈썹·머리카락이 어떻게 연결되어 있는지 확인한다. 텍스처에 그려진 부분과 분리된 메시를 구분한다.
- 기준 중립 얼굴의 정면·양측면·3/4 근접 이미지를 저장한다. 랜드마크를 추정하면 실제 메시와 이미지에 투영해 위치를 검토한다. 눈·입 위치를 바운딩 박스 비율로만 추정해 바로 변형하지 않는다.

### 기능은 하나씩 만든다

1. 좌우 눈 깜빡임: 중립→중간 닫힘→닫힘→중립을 시험한다. 눈꺼풀이 안구를 관통하거나, 주변 얼굴을 과도하게 끌거나, 눈 텍스처만 찌그러지는지 확인한다.
2. 시선: 실제 움직일 수 있는 안구 구조가 확보된 경우 좌우·상하와 중립 복귀를 시험한다. 별도 안구가 없으면 그 사실을 기록하고 다음의 국부 재구성 분기에서 처리한다. 고정된 눈 그림을 실제 안구 제어로 표시하지 않는다.
3. 턱과 작은 입 벌림: 입술·턱·입안의 실제 구조가 허용하는 범위부터 시험한다. 턱 회전과 형상키가 같은 변형을 중복 적용하지 않게 한다. 입안이 없는데 큰 입 벌림을 억지로 만들지 않는다.

기존 기하가 부족하면 별도 얼굴 실험본에서 안구·눈꺼풀·입술 경계·간단한 입안의 국부 보강을 시도할 수 있다. 통째로 다른 얼굴이나 외부 캐릭터로 교체하지 않는다. 연결된 입술을 다루는 작업은 실제 토폴로지 수정 실험으로 기록한다. 정점 이동만으로 새 입안이나 분리된 경계가 생겼다고 가정하지 않는다.

구조 변경은 최종 형상키 작성 전에 정리한다. 이후 정점 수·순서·토폴로지를 고정하고 모든 키가 같은 기준 메시를 사용하게 하라. 뒤늦은 리메시·Decimate로 키가 깨지거나 얼굴 외 영역이 영향을 받는지 확인한다. 필요한 국부 수정으로 UV·무늬가 달라지면 그 영향도 비교한다.

눈꺼풀/입술을 안정적으로 구성하지 못하면 해당 기능을 BLOCKED_TOPOLOGY 또는 FAIL로 기록하고 가능한 기능은 남긴다. 눈이나 입을 닫을 수 없는데 제어 슬라이더만 있다는 이유로 완료하지 않는다. 사용자에게 정점을 수동으로 찍거나 얼굴을 직접 수정하라고 요구하지 않는다.

첫 번째 유효한 얼굴 기능이 나오면 작은 FBX 내보내기와 재수입 검사를 먼저 수행한다. Unity에 접근할 수 있으면 Unity 재생까지 확인한 뒤 확장한다. Unity에 접근할 수 없으면 Unity 검증만 UNVERIFIED로 남기고 Blender에서 가능한 얼굴 확장은 계속한다. 확인된 내보내기 결함은 그 경로에 의존하는 확장 전에 해결하거나 해당 경로의 한계로 기록한다.

## 6. 단계 D — 소수의 표정과 몸 동작의 결합

기초 얼굴 기능을 통과한 부분만 확장한다. 처음부터 ARKit 52종이나 대사 립싱크를 구축하지 않는다.

- 가능한 기능으로 미간 찌푸림, 눈썹 올림, 눈 가늘게 뜸, 입꼬리 미세 상승, 입술 다물기/긴장 정도를 만든다. 좌우 독립이 필요한 기능은 분리한다. 구체적인 키 이름과 중복 여부를 정해 기록한다.
- 표정 프리셋은 집중, 경계, 가벼운 냉소, 통증 등 최대 4개를 구성한다. 이는 실험용 표정이며 도사 얼굴의 새로운 디자인 승인으로 간주하지 않는다. 기초 기능이 부족하면 가능한 프리셋만 구현한다.
- 각 채널을 0/25/50/75/100%와 중립 복귀로 검사하고, 미간+깜빡임, 시선+깜빡임, 턱+입술 등 실제로 쓸 조합을 시험한다. 강도는 의도한 최대 범위로 정의하고 변형 붕괴를 감추기 위해 시험값을 임의 축소하지 않는다.
- 얼굴 인상, 눈꺼풀 접촉, 입술 접촉, 수염·눈썹의 동행, 목과 머리 경계, 재질·노멀을 정면·측면·3/4에서 비교한다. 모든 제어가 0일 때 기준 중립 얼굴로 돌아오는지 확인한다.
- Idle·Run·Attack 중 깜빡임과 표정을 함께 재생한다. 머리 움직임으로 얼굴 제어가 이중 적용되거나, 애니메이터와 별도 제어기가 같은 채널을 덮어쓰는지 확인한다.

## 7. Blender → FBX → Unity의 실제 확인

- Blender의 제어용 본, 제약, 드라이버와 최종 런타임 변형 데이터를 구분한다. 필요한 본 애니메이션과 형상키 변화는 내보낼 수 있는 데이터로 만들고, 런타임 제어가 필요하면 실제 Unity 제어 코드까지 구현한다. Blender의 드라이버가 그대로 실행될 것이라고 가정하지 않는다.
- FBX를 빈 장면에 재수입하여 단위·좌표·골격·스키닝·얼굴 키와 대표 조합을 비교한다. 정점 순서가 바뀌었다면 단순 인덱스 비교를 강행하지 말고 대응 가능한 방법을 사용하거나 비교의 한계를 기록한다.
- 별도 Unity 실험 프리팹에서 실제 Humanoid 매핑, 원본 클립, 추가 본과 BlendShape 존재·이름·강도 제어를 확인한다. Blender 키 강도와 Unity BlendShape 강도의 범위를 명시적으로 변환한다.
- 테스트 초기에 최적화·압축에 의해 필요한 본이나 표정 데이터가 누락되지 않는지 확인한다. 프로젝트에서 최적화를 켠 최종 설정도 별도로 검증한다. 복제 아바타의 골격이 맞는지 확인 없이 공용 Avatar를 재사용하지 않는다.
- 몸은 Animator로, 표정은 명시한 표정 제어 경로로 동시에 재생한다. 테스트 UI에 기능별 조절과 중립 복귀를 제공하되, 원본 게임 UI·PlayerRig에는 섞지 않는다.
- 실제 게임 카메라 설정을 확인해 그 거리에서도 보여라. 게임이 1인칭이라 전신이 보이지 않으면 전신 검수용 카메라를 별도로 제공하고, 존재하지 않는 3인칭 플레이 화면을 실제 게임 화면이라고 부르지 않는다. 얼굴 근접 검사도 별도로 유지한다.
- 렌더 삼각형, 변형 본 수, BlendShape 수, 머티리얼/렌더러 수를 기록한다. 성능 수치를 측정했으면 플랫폼·실행 조건을 함께 남긴다. 이 통계만으로 중고사양 PC 성능 합격을 선언하지 않는다.
- Unity를 실행할 수 없다면 Blender에서 수행 가능한 단계는 끝내고 Unity 항목만 UNVERIFIED로 남긴다. Blender 미리보기를 Unity 실시간 캡처라고 표시하지 않는다.

Unity는 FBX로 가져온 BlendShape를 SkinnedMeshRenderer에서 제어하고 애니메이션할 수 있다. 따라서 표정은 Blender 내부 슬라이더뿐 아니라 실제 가져온 데이터와 재생을 검증 대상으로 삼는다. 근거: [Unity BlendShape 문서](https://docs.unity3d.com/6000.0/Documentation/Manual/BlendShapes.html).

Humanoid 매핑과 가져오기 옵션은 실제 프로젝트 버전에 맞춰 확인한다. 참고: [Humanoid 가져오기](https://docs.unity3d.com/6000.0/Documentation/Manual/ConfiguringtheAvatar.html), [Rig 가져오기 설정](https://docs.unity3d.com/6000.0/Documentation/Manual/FBXImporter-Rig.html). 문서의 기능 지원을 이 모델의 품질 보증으로 해석하지 않는다.

## 8. 결과 저장·판정·작업 종료

단계별 가장 나은 검증본과 실패 실험을 구분해 보존한다. 단순히 마지막으로 저장한 파일을 Best로 지정하지 않는다. 작은 변경은 관련 검사부터 하고, 단계 체크포인트에서 몸/옷과 이미 통과한 얼굴 기능의 회귀를 확인한다.

최소 전달물:

- 원본 기준본과 단계별 편집용 .blend, 실제 내보낸 .fbx, 사용 텍스처.
- 재실행 가능한 Blender 스크립트, 필요한 Unity 실험 코드·씬·프리팹. 동일 스크립트를 재실행해 본·키·머티리얼이 중복 생성되지 않도록 한다.
- 실험 기록: 가설, 변경 영역/방법, 결과, 회귀, 채택·되돌림, 시도 횟수. 결과 파일과 영상이 어느 모델·클립 버전에서 나왔는지 식별 가능하게 한다.
- 몸/옷 수정 전후 동일 조건의 비교 영상, 루프·전환 영상, 얼굴 채널/표정 영상, Unity 통합 재생 영상 중 실제 수행한 자료. 기본 영상은 16:9, 1280×720 이상, 원래 시간 속도로 제공한다. 얼굴은 같은 화면 비율의 근접 구도로 보여라.
- 일반 검수 영상에는 텍스트·라벨을 넣지 않는다. 경고 부위를 색으로 표시한 진단 영상은 별도로 제공하고, 설명·프레임 번호·단계 상태는 REVIEW.html의 이미지 밖에 둔다. 기준 경고 위치가 보이는 시점도 함께 제공한다.
- 실제 미디어를 포함한 REVIEW.html과 간결한 FINAL_REPORT.md. 갤러리의 상대 경로가 실제 전달 폴더에서 열리는지 확인한다. 정지 이미지나 프레임 나열을 연속 MP4로 부르지 않는다.

판정은 항목별로 PASS / FAIL / UNVERIFIED / NOT_ATTEMPTED를 기록하고, PASS에는 반드시 시험 범위를 덧붙인다. 필요한 구조를 만들지 못한 기능에는 BLOCKED_TOPOLOGY를 원인으로 남길 수 있다.

| 항목 | 합격 판단 대상 |
| --- | --- |
| body_clothing_deformation | 같은 기준 동작의 실제 어깨·소매·자락 개선, 잔여 결함과 회귀 |
| animation_naturalness | 원속도 동작·발 접지·루프·전환의 실제 비교 |

| face_blink / face_gaze / face_jaw | 각 기능의 실제 동작과 중립 복귀 |
| face_expressions | 구현한 표정과 조합의 실제 변형 |
| fbx_roundtrip | 내보낸 데이터의 보존; 캐릭터 외형 합격과 별개 |

핵심 결함이 있는 통합 모델을 합격으로 바꾸지 않는다. 다만 얼굴 하나의 실패 때문에 통과한 몸/옷 또는 다른 얼굴 기능까지 폐기하지 않는다. 예를 들어 ‘몸/옷 개선 및 깜빡임 확인, 입 벌림은 구조 부족, Unity는 미실행’처럼 도달 지점을 구체적으로 보고하라.

종료 시 결과 링크와 함께 다음만 먼저 요약하라: 실제로 좋아진 부분, 여전히 실패하거나 미검증인 부분, 가장 나은 파일, 다음 실험을 막는 구체적 구조·도구 제약, 실제 추가 비용. 이번 실험의 추가 유료 요청은 0이어야 하며 기존 123크레딧을 새 비용으로 집계하지 않는다.

실제 모델 접근이 불가능하면 이미지로 메시·웨이트·얼굴 구조를 추측하여 작업을 완료한 것으로 쓰지 않는다. 접근 가능한 자료의 분석과 실행 준비를 끝낸 뒤, 필요한 실제 파일 또는 연결을 한 번에 구체적으로 알려라. 중요한 외형 교체가 꼭 필요하면 먼저 비교 가능한 결과를 만들고 그 디자인 판단만 사용자에게 요청하라.
